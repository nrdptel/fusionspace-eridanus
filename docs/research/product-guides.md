# Product guides: each product, illustrated

**Bottom line:** rocketry tools document themselves with screenshots that need refreshing
(OpenRocket refreshed its documentation screenshots in [PR #3367][or-3367], merged 2026-09-30)
or with one long manual. RASAero II's is a 154-page PDF from 2019, and altimeter makers publish
a PDF per board revision. The best pages in the field are RocketPy's worked examples, which end
on a real flight. hpr has almost no product visuals: two figures in its pages, one of them
regenerated by CI, no landing page per product, and no release milestone that asks for a guide.
Each product should get a landing page and an illustrated tour whose every picture a command
makes and CI reruns. Where each piece goes is in [ADR-196, the product guides][adr-196].
Researched October 7, 2026.

## What hpr has

- **The products:** the simulator (library, CLI, Python) ships in 0.1, the flight analyzer in
  0.2 (diagnosis in 0.3), the competition kit with the field kit in 0.4, the app in 0.5 and 1.0;
  the motor and recovery designers and the avionics line after 1.0 ([ADR-163][adr-163] §1).
- **The pages:** the simulator has a tutorial (*Getting started*), task pages for the CLI, the
  builder, Monte Carlo, optimization, weather and export, and the API reference. The site lists
  them flat; no product has a page of its own.
- **The pictures:** `sim-plot.svg`, which `xtask cli --check` regenerates, and
  `flight-phases.svg`, drawn by hand. CLI output appears as text blocks that the same command
  regenerates, so a stale one fails the gate. Nothing makes screenshots.
- **The release checklist** ([ADR-162][adr-162] §2) asks only for the changelog entry and the
  install pages.
- **The product system** asks documentation sites to use its mdBook theme and to open each page
  with what works and how far to trust it (`web.md`). Manuals use its signal-word panels
  (`writing.md`). It has no rule for screenshots beyond store images in the default appearance.

## How other tools do it

| Tool | Form | Visuals | Weakness |
|---|---|---|---|
| [OpenRocket][openrocket] | Sphinx site: setup, user guide, developer guide | Screenshots, refreshed in batches | The older wiki has empty sections |
| [RocketPy][rocketpy] | Beginner's guide, user guide, API, examples | Plots from executed notebooks | Few diagrams; heavy on the API |
| [RASAero II][rasaero] | One PDF, 154 pages, 2019 | About 190 screenshots | Unchanged since 2019, not searchable online |
| [RockSim][rocksim] | Help shipped with the program, videos | Screenshots, video | Spread across versions |
| [Altus Metrum][altos] | One HTML and PDF manual, October 2025 | Board photos, screenshots | One long manual; no flight walkthroughs |
| [Blue Raven][blue-raven], Eggtimer | A PDF per board and firmware revision | Photos, phone screenshots | Readers must find the right PDF |

## Lessons

1. **Split by what the reader needs** ([Diátaxis][diataxis]): a tour, task pages, reference,
   explanation. hpr already sorts its pages this way; the products need a front page each.
2. **End the tour on a real flight.** RocketPy's [Valetudo][valetudo] page, a simulation against
   the measured flight, is the most convincing page in the field. hpr's tour uses a public flight
   from its validation cases, never a private one.
3. **Make every picture with a command,** so it cannot go stale unseen. Blender's
   [manual rules][blender] help: the default interface, no text baked into images, labels in
   captions.
4. **Test the docs.** Code, output and pictures rerun in CI, so a guide that drifts fails the
   build, as hpr's `xtask cli --check` already does for text.
5. **One manual per release** (Blender, KiCad) keeps readers off the wrong version; hpr's guides
   say which version they describe, and a versioned copy per release waits in the backlog.

## Tools for the pictures

- **App screens:** [Playwright][playwright] (Apache-2.0) captures pages from end-to-end tests,
  hides changing regions and can measure each element's box. It has no model of a device's safe
  area, so the check compares those boxes with the platform's published insets and corner radii.
- **CLI:** `xtask` draws the output it already captures as terminal figures in SVG, offline and
  deterministic. [VHS][vhs] (MIT) can record animations later; asciinema's recorder is GPL-3.0,
  so at most a build tool, never a dependency.
- **Plots:** hpr's own plot writer, as `sim-plot.svg` is made now.
- **Avoid:** [Doc Detective][doc-detective]'s core is AGPL-3.0.
